# 2026.11.13

A full bench of the signed 2026.11.13 release images on every board of the dev box rig, on 2026-11-20 (run `20261120-062810`, `bench.py run --rediscover --full`, about two hours). It is compared with 2026.11.12 and with `2026.11.12+3f3bdac79` (the desktop-windows build, run `20261119-203549`), the last full run before it.

- **Boards:** SenseCAP Indicator D1, reTerminal E1002, E1003, E1004 and Sticky, flashed with `frameos-2026.11.13-esp32-s3-{generic,32mb}-app.bin`. The Inky Frame 7.3 Spectra (Pico 2 W) is a thin client and stayed on `2026.11.12-main.e0a754bd0`.
- **Backend:** the self-hosted backend at the release commit (`c4d6bb12b`), with the release's wasm runtime (`frameos-2026.11.13-wasm.tar.gz`) rendering the Pico's scenes.
- **Suites:** status, reboot, benchmark, scenes, builtin, input, desktop, code, storm, soak and offline. `--full` means nothing was sampled on the slow e-paper panels.
- **Verdict:** 0 crash, 4 fail, 29 slow, 28 note.

## Better

- **No crash on any board, in a full run.** This is the first release where that holds for the E1004. On 2026.11.10, .11 and .12 its full runs had 9, 19 and 10 crashes, mostly running out of memory in the desktops. Behind the change are the desktops' window limit by memory (one window on the E1004) and dropping a parked layout, both from FrameOS#909. The SenseCAP's `LoadProhibited` panic in the Windows 98 desktop on the desktop build is also gone. That was the `imageFromJsx` use-after-free, fixed in FrameOS#911.
- **SenseCAP responsiveness 1540 → 2930.** The scene switcher opens in 186 ms, down from 2,405 ms on the desktop build and 1,498 ms on 2026.11.12. Scene settings open in 100 ms, down from 1,002 ms.
- **More memory on every board.** The lowest free PSRAM during the benchmark rose 0.15–0.22 MB on every board compared with 2026.11.12:

  | board | 2026.11.12 | 2026.11.13 |
  |---|---:|---:|
  | E1004 | 1.69 MB | 1.85 MB |
  | Sticky | 3.85 MB | 4.09 MB |
  | E1003 | 4.17 MB | 4.39 MB |

  The largest free PSRAM block grew by 0.1–0.3 MB. This lines up with the glyph cache (FrameOS#912, #913: 4-bit glyph masks instead of kept outlines, and the built-in face read in place).
- **Boot to first picture a little faster** on the E1003 (24.8 → 21.4 s), the E1004 (32.5 → 30.4 s) and the Sticky (24.0 → 21.4 s), compared with the desktop build.

## Worse

### The E1003's UI scenes repaint the whole canvas on every render

Every UI scene on the E1003 has a fastest warm render about 2.4× slower than on the desktop build, for example:

| scene | desktop build | 2026.11.13 |
|---|---:|---:|
| Counter | 169 ms | 400 ms |
| Calculator | 145 ms | 376 ms |
| Home | 132 ms | 336 ms |

The same happens to Touch test, Render counter, Colors, Steps, Tap counter, Gallery, To-do, Weather demo and Form showcase. The per-phase probe shows where the time went:

- **Desktop build:** after the first warm render (raster 254 ms), the next ones raster about 96 ms. That is the damage repaint, which draws only what changed.
- **2026.11.13:** every warm render rasters about 322 ms, a whole repaint, and the first one is slower too (323 ms).

The Sticky, also e-paper, didn't change (raster 107–117 ms after the first), and neither did the LCD. So the regression is specific to the E1003's sixteen-grey `pfGray4` canvas.

The glyph cache's 4-bit masks (FrameOS#912, #913) are the first suspect: they changed how text reaches that canvas between the two builds. It isn't bisected yet.

### A scene installed right after another push can be dropped by the board (E1002: 4 fails)

The Code editor suite installs the editor as a one-scene patch, right after the previous suite pushed the frame's own scenes back. On the E1002 the editor never opened:

1. The earlier full set (186,646 bytes) was taken at 814.9 s and was still waiting on the store task when the editor's patch arrived (822.1 s, `pending-apply`).
2. The patch reached the catalog. Then the older set's write landed at 823.5 s, `as-changes: 4 written at once, 0 kept, 1 dropped`, which dropped the editor.
3. The board keeps the patched checksum, so every later sync from the backend gets a 304. Selecting the editor fails with `apply-failed` at 823 s, at 1,008 s and at 1,194 s: the board and its backend now disagree until something else changes.

In the previous run on the desktop build, the older set had finished writing before the patch arrived, so this is a race and not new code. One run can't tell whether 2026.11.13 makes it more likely. It is a firmware bug in `fos_scene_store` / `fos_scenes.c`: a patch must apply to the set it names, and a write still waiting must never overwrite a newer change.

### JSON is 11–14 % slower than on 2026.11.12, on every board

The CPU benchmark's JSON loop (stringify and parse of 200 rows):

| board | 2026.11.12 | desktop build | 2026.11.13 |
|---|---:|---:|---:|
| SenseCAP | 1,193 ms | 1,259 ms | 1,343 ms |
| E1002 | 1,117 ms | 1,196 ms | 1,267 ms |
| E1003 | 796 ms | 846 ms | 886 ms |
| E1004 | 1,083 ms | 1,169 ms | 1,241 ms |
| Sticky | 802 ms | 845 ms | 890 ms |

The integer, float and string loops didn't move, so CPU scores are down 1–3 %. The slowdown came in two steps, part before the desktop build and part after, so it isn't a single change. QuickJS's JSON is the place to look, along with what links next to it (`embedded/esp32/link_order.txt`).

### Smaller

- **E1004, Flights above me:** fastest warm render 6.7 → 11.2 s. The scene fetches live data, so the network may account for some of this.
- **SenseCAP DVD logo:** 21.8 fps (23.6 on the desktop build), against a 30 fps target. A quiet frame is 42.7 ms of scene time, 39.5 ms before.
- **E1002 internal RAM:** the lowest free since boot fell from 28.2 KB (11.12) to 23.1 KB, and the largest block from 24 KB to 18 KB. The SenseCAP's went the other way, 12.0 → 13.7 KB.

## Unchanged, still worth knowing

- **E1004 memory:** it still discards JavaScript interpreters for low memory throughout (16 in the benchmark, 50 in the soak). It renders a 1200×1600 canvas with 1.3–2.0 MB of PSRAM free. The large photo and clock scenes take 38–43 s a render.
- **SenseCAP internal RAM:** too little for its HTTPS server, which skips startup for low memory, as on every build since 2026.11.10. Desktop pushes to it are refused as patches (no room on its 1 MB `/state` beside the set) and go as the whole list instead, as before.

## Follow-up (2026-11-20)

### The E1003's UI scenes: fixed in FrameOS#923

This wasn't the damage repaint. The render line showed the glyph cache missing nearly every glyph on every render: `glyphs 4/59 62K`, then `glyph 63x279 ms`.

- **The budget:** the E1003's scenes wear a layout, and at 1872×1404 the layout and a scene draw 69–83 KB of glyph masks. The ESP32's glyph cache budget was 64 KB.
- **LRU:** when a render needs slightly more than the budget, least-recently-used eviction puts out each glyph just before the same render draws it again.

FrameOS#923 makes the budget grow with the panel's area (up to 256 KB), and makes a miss never evict a glyph the same render drew. On the E1003, warm renders went back to where they were before the glyph cache:

| scene | 2026.11.13 | FrameOS#923 |
|---|---:|---:|
| Counter | 400 ms | 167 ms |
| Calculator | 376 ms | 142 ms |
| Home | 336 ms | 132 ms |

### The dropped scene: fixed in FrameOS#925

A one-scene change now waits for a backend set the store task is still writing. On the E1002 the Code editor suite went from 4/4 failed to passing in three runs, and the last run logged the wait it made: `a change waited 1323 ms for the backend set's write`.

### JSON: code placement, not a code change

QuickJS didn't change between 2026.11.12 and 2026.11.13, and neither did the CPU benchmark's other three loops. I built the release's own code with nothing changed but `embedded/esp32/link_order.txt`, which decides where each object sits in flash, and ran the benchmark suite (five warm renders, right after a reboot) on the same boards:

| build (same code) | E1002 JSON | E1003 JSON | int / float / str |
|---|---:|---:|---|
| 2026.11.13 release (its link order) | 1,267 ms | 886 ms | — |
| link order written again from the current build | 1,166 ms | 829 ms | within 1 % |
| written again from that build (a second round) | 1,380 ms | 968 ms | within 1 % |

Each run's five samples are within ±2 %. So moving the code around, and nothing else, makes JSON ±10 % faster or slower. 2026.11.12's fast JSON (1,117 ms, 796 ms) came in with a fresh link order (FrameOS#886), and every build since has moved things again.

The S3 runs code from flash through a 16 KB, 8-way instruction cache. The JSON loop is the one that leans on code outside `quickjs.c`: `dtoa.c` turns the rows' `i * 1.5` into text and back, and `cutils.c` grows the buffers. Their distance from `quickjs.c` is what the link order changes, while the integer, float and string loops stay inside the interpreter. That is the likely mechanism; I haven't proved it with cache counters.

What to do with it:

- **The benchmark:** a JSON change under about 10 % between builds is placement noise, not a regression. A refreshed link order is a lottery for this loop and needs the benchmark run after it. It isn't a fix.
- **A real fix** would make the JSON path's hot code contiguous, so its cache sets don't depend on the base address. That means QuickJS's JSON, string buffer, allocator and `dtoa` functions placed together, which needs function-level ordering in `tools/link_order.py` (today it orders objects). Or put the hottest of them in IRAM. A 32 KB instruction cache would also help, but it costs 16 KB of internal RAM, which the SenseCAP doesn't have.
