# main e12f082

A full bench of main `e12f08280` on every frame on the dev box rig, on 2026-11-27 evening, after the fourth UX bench of the day. It is compared with the afternoon's full run of main `c9a51bf` (`20261127-135642`). Main in between is the third UX bench's fixes (frameos#1118–#1132): samples, the keys' paging (#1118), JSX truncate (#1127), render/text "fit" keeping words whole (#1131), and an ESP32 scene switch that drops the old scene first when it finds no room (#1132).

- **Run:** `20261127-202035`, `bench.py run --rediscover --keep-booked --baseline 20261127-135642`. Every suite on every frame; the E1002 and E1004 sampled as usual.
- **Boards:** all twelve ESP32s on local builds of `e12f082` (`firmware/build.sh`, ELF `eb2acad4`), flashed one at a time with `flash_checked.sh` (`firmware/flash-main-e12f082.sh`, 19:32–19:44), all twelve verified.
- **Pico:** stays on `2026.11.12-main.e0a754bd0`.
- **Pis:** Cloud-W cross-built from `e12f082` (armv6, `release_main_e12f08280`; drivers the live release's, `driver_abi.nim` unchanged). Its `/srv/frameos` is 94 % full: prune old releases before the next install. Cloud-5: no route to host.
- **Backend:** the bench backend's code unchanged (no backend commits since `c9a51bf`), its wasm runtime rebuilt from `e12f082` (`wasm-main-e12f082`); frames 1–6 given the repo's samples (`update_scenes.py --apply`).
- **Verdict as printed:** 2 crash, 1 fail, 30 slow, 19 note.

## Fixed since the last run

All three fails of `20261127-135642` are gone: Cloud-W Files' render timeout (frameos#1124, a bench fix) and the Sticky's switches to Handwriting notes and Pixel art after Hacker News (frameos#1132: the switch drops the old scene first).

## Crash, fail

- **crash `oom` (×2, one event), Sticky, code suite:** the Code editor opening Browser asked for one 227,318-byte block (`remember` of the whole work in `setWork`) with 1,078,080 bytes of PSRAM free and the largest block 216 KB, an hour into the bench. The runtime refused it cleanly (the editor showed its error; no restart). The same step passed in the last run with the same sources (Browser's scenes.json 194.0 → 194.7 KB): fragmentation decides it. The cause to fix is the Code editor keeping a scene's whole sources as one remembered string.
- **fail `desktop_push`, SenseCAP, layout-classic-mac:** the device did not take the pushed scenes in time (one layout of seven, the board busy animating). Passed in the last run; intermittent.

## Slow

- **Sticky UI tap 410 → 554 ms, E1003 407 → 504 ms** in this run's benchmark: an A/B on the Sticky in turn (`~/.frameos-bench/ab-sticky`, c9a51bf, e12f082, c9a51bf, e12f082) gave 404 / 404 / 402 / 405 ms and warm UI renders 137 / 141 / 135 / 142 ms. **No regression**: the full run's numbers came from the board's state then.
- **Idle memory:** the E1003 idled on Gallery (1.9 MB less PSRAM free: Gallery keeps its decoded photos) and the Sticky on Pixel art, where the last run had Analog clock face and Calculator: the UX bench's hardware checks before this run left them there. Not the firmware.
- **Regressions flagged by `compare`:** Sticky Hacker News fastest warm 200 → 335 ms and E1004 Wikimedia Commons 15.1 → 20.7 s: both samples changed in between (frameos#1130).
- As before: the E1004's photo scenes (15–34 s warm renders), the Code editor on the E1004 (24–33 s), Pixel toys under its fps targets on the LCDs (Advance 7.0" 12.8 fps, AMOLED 14.0, SenseCAP 28.2, rotary 39.8), restarts after a rotation 30–58 s on the e-paper boards, Cloud-W's desktop switches waiting 7.7–9.7 s.
