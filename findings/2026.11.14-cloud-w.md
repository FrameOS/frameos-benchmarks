# 2026.11.14 on a Raspberry Pi Zero W (cloud-w)

The first Linux frame on the bench: a Raspberry Pi Zero W with a Pimoroni HyperPixel 4 Square (720x720 touch), benched on 2026-11-24 against the five ESP32 boards' 2026.11.14 runs ([2026.11.14.md](2026.11.14.md)).

- **Frame:** cloud-w, Raspberry Pi Zero W Rev 1.1 (BCM2835, one ARM1176 core, 512 MB), Buildroot 2025.02.13. It runs at **700 MHz**: the image's `powersave` governor, of 1 GHz. Its framebuffer is 16 bpp, so the runtime draws in the panel's RGB565 canvas (`in place`).
- **Build:** the signed `frameos-2026.11.14-debian-bookworm-armv6` release. It printed `2026.11.14+1ea54241…`, the release's `versions.json` hash, and is recorded as `2026.11.14`. It was upgraded from a 2026.11.7 test build with `frameos upgrade --yes`, run under `systemd-run`. The 2026-11-22 upgrade had died inside the service's cgroup.
- **Attached:** adopted into the bench backend as frame 7 (`POST /frames/adopt`), with its 20 cloud-pushed scenes copied in and pushed. The layout chosen on the frame (macOS) was taken off. Its FrameOS Cloud link stays connected.
- **How:** over SSH, not USB (`tools/frame-bench/framebench/linux.py`, `bench.py run --linux-only`): its journal is the console, its HTTP API takes the commands, and each line carries the frame's own time.
- **Runs:** `20261124-024311` and `20261124-031652`, both `--full`, every default suite, about 55 minutes each. The trial runs before them were not recorded.
- **Verdicts:** run 1: 5 crash, 1 fail, 2 slow, 4 note. Run 2: 0 crash, 2 fail, 4 slow, 4 note.

## Findings

1. **Intermittent SIGSEGV after a push over HTTP** (crash). In run 1, three of the settings suite's seven pushes (the rotation to 90°, the Tiling layout, no layout) killed the runtime. Each time the backend's fast deploy sent `POST /api/frames/1`, the runtime reloaded and rendered, the second `POST /api/frames/1` (the metadata echo) arrived about a second later, and within two seconds came `SIGSEGV: Illegal storage access. (Attempt to read from nil?)`, then `code=dumped, status=11/SEGV`. No other push crashed: the other 4 there, all 7 settings pushes in run 2, and all 18 desktop-suite pushes across both runs. It looks like a cross-thread race between the frame API's handler and the config reload, of the kind AGENTS.md calls "Refs do not cross threads". No core was kept (`core_pattern` is `|/bin/false`). The raw log is `20261124-024311/Cloud_W.raw.log`, around +998 s, +1640 s and +1666 s.
2. **The render log pause hides the first render after a fast scene.** runner.nim stops logging renders for ten seconds after two fast ones, and turns logging back on only after a render of a slow scene ends. So the switch away from an animation is never logged: no `render:done` reaches the backend for it. A scene that ticks itself faster than its interval (Rainbow clock's `nextSleep`) counts as fast and keeps the pause going, as does a desktop with an animated window open. The bench works around it (`bench:unlogged`, the switch reported untimed). The runtime fix is to turn the logger back on at a scene change.
3. **The scene snapshot's PNG encode blocks the runner after every switch**: 0.5–1.3 s for a UI, 3.2 s for a photo (Cuteness Overload, a 516 KB PNG). Every event in that window waits behind it. The switcher opened in 3.4 s for a 121 ms render. The Code editor's first open took 6.6 s for an 809 ms render. A `render` right after a switch waited 467 ms.
4. **Adoption's restart gets a 401.** `_restart_adopted_runtime` posts `/event/restart` before the device has reloaded the config that carries its new `serverApiKey`: on a Pi Zero the reload waits for the render pass and its snapshot. It did no harm here, because 2026.11.14 picks the backend up for its logs at the reload.
5. **A push over HTTP makes frame.json about 800 KB.** `frameApi.last_successful_deploy` holds the whole scene set (649 KB), and every config read parses it.
6. **The Pi Zero W runs at 700 MHz.** The Buildroot image leaves it on the `powersave` governor. `ondemand` would give up to 1 GHz when it renders, and probably about a third more on CPU-bound work. Not measured.
7. **The resident set rose every soak round**, from 61.8 to 64.9 MB over five rounds of all 16 scenes in run 2 (`leak`). That is 0.75 MB a round, possibly caches filling up (each scene's snapshot thumbnail, the glyph cache). A longer soak would tell.
8. **The animations miss 30 fps at 720x720.** DVD Logo Bounce ran at 20.6–24 fps (34–44 ms frames), JSX: DVD bounce at 21–23.5 fps.
9. **A bench bug, found here:** the input suite asked for `{"direction":"previous"}`, but the contract's directions are `next` and `prev`, so every board refused it (`event:refused`, `direction`). The ESP32 runs recorded a time for it only because a scene that ticks (the E1003's clock) rendered anyway. It is fixed in the same change as the Linux path, and the metric is still `resp.input.previous_ms`.
10. **SSH:** the Pi Zero's dropbear stopped answering for about a minute after a burst of new logins. The bench keeps one shared connection.
